# 🧭 Maxgraph Protocol — порядок работы агента с памятью

Этот протокол обязателен для каждой сессии агента, подключённого к Maxgraph.

## 1. Старт сессии

1. Прочитать `MEMORY.md` (локальный контекст-ускоритель)
2. `session_start(project=<slug>)` из Maxgraph — бюджетный блок контекста проекта (`context_block` ≤ `budget_chars`, default 10 000): `# Проект` → `## Решения владельца` → `## Открытые баги` → `## Открытые задачи` → `## Прошлые сессии` → `## Недавние события`. `read_graph` — только когда нужен весь граф целиком или slug неизвестен
3. Если граф недоступен → работать с локальным кэшем и восстановить синк при появлении связи

### 1.1 Проекты (изоляция, Ф1)

Каждая запись памяти может принадлежать проекту (kebab-slug: `kimi`, `maxgraph`…).

- **Откуда slug**: хост (хук DSH/Claude Code) определяет каскадом git remote → git root → имя cwd; агент получает готовый slug. Сам сервер slug не вычисляет.
- **Как указывать**: параметр `project` в КАЖДОМ вызове MCP (`session_start`, `create_entities`, `add_observations`, `create_relations`, `read_graph`, `search_nodes`, `list_timeline`, `delete_*`, `update_entity`, `open_nodes`); в REST — `{"project": "<slug>"}` в теле POST или `?project=<slug>` в GET.
- **Автосоздание**: первая запись со slug создаёт сущность `project:<slug>` (entityType `project`, title = slug) и связывает новые сущности с ней `part of`.
- **Изоляция чтения**: `read_graph`/`search_nodes`/`list_timeline` с `project=X` видят только проект X; `all_projects=true` — явный кросс-поиск по всем проектам; вызов без `project` — плоский граф целиком, как раньше (default-проект не навязывается).
- **Имена глобально уникальны**: имя сущности уникально по ВСЕМ проектам — одноимённую сущность во втором проекте создать нельзя (`create_entities` → `skipped` + `warnings[]`, merge не происходит; аудит 2026-10-25). Нужен «такой же» объект в другом проекте — давайте имя с префиксом проекта (`kimi-deploy` vs `maxgraph-deploy`). Легаси-сущность без проекта при первом merge с `project=X` принимает проект X (`adopted` в ответе).
- **Новый проект = пустой граф**: старые сессии/факты других проектов НЕ подтягиваются; проект создаётся на стороне хоста (папка воркспейса → хук/агент пишут с `project=<slug>` → `project:<slug>` появляется автоматически), дашборд — только просмотр.

### 1.2 Типы и статусы (Ф3, В2.1)

Канонические типы: **`project` / `session` / `bug` / `decision` / `request` / `event` / `task`**.
Синонимы RU/EN канонизируются на границе записи (`bugfix`/`fix`/`баг`/`ошибка` → `bug`,
`решение` → `decision`, `просьба`/`запрос`/`хотелка` → `request`, `событие` → `event`,
`todo`/`задача`/`туду`/`дело` → `task`…, полный словарь — `_TYPE_SYNONYMS` в `app/app.py`).
Свободные типы (`file`, `service`, `capability`…) не запрещены и остаются как есть —
но каноника фильтруется в поиске (`search_nodes(type=…)`, ответ включает канонический
`type`, для `bug`/`task` — `status`) и чипами-табами в дашборде.

| Тип | Когда использовать |
|---|---|
| `project` | Только структурная сущность `project:<slug>` — создаётся автоматически, руками не плодить |
| `session` | Сессия с итогом: `session-YYYY-MM-DD-<slug>`, факты = итоги, связи `discussed` |
| `bug` | Дефект/уязвимость, требующий исправления. **Явный статус: `open`/`fixed`** (default `open` при создании; закрытие — `update_entity(status="fixed")`) |
| `task` | **Открытое дело «на потом»** (work_state, В2.1): задача, которую надо не забыть. **Явный статус: `open`/`done`** (default `open`). Создание — `task_add(project, title, note?)` (имя `task-<slug(title)>` автоматически), закрытие — `task_done(project, name)`, список открытых — `task_list(project)`. Открытые задачи видны в `session_start` («Открытые задачи», кэп 10) |
| `decision` | Решение (особенно владельца). **Решения владельца — дословно (verbatim)**, без перефразирования; причина — отдельным фактом |
| `request` | Просьба/требование владельца, ещё не выполненное; выполненное — факт с датой на той же сущности |
| `event` | Событие «произошло»: реализованная фича, рефакторинг, миграция, выясненный durable-факт |

Для остальных типов `status` игнорируется с warning (правило «status только для bug»
расширено на bug+task в В2.1).

`session_start` читает статус бага ЯВНО: `fixed` баг не попадает в «Открытые баги»
без всякой эвристики; эвристика (тег/последнее статусное слово) — только фоллбек
для legacy-багов без поля `status`. Аналогично `done` задача не попадает в
«Открытые задачи».

### 1.3 После сжатия контекста — ре-прайм

Харнесс может сжать диалог: заменить начало разговора автоматическим summary.
Признаки: сообщение-чекпоинт `<compacted-summary>` (DSH), продолжение после
`/compact` (Claude Code), любое машинное «вот о чём мы говорили» в других клиентах.
Сжатие съедает детали — включая правила, которые не записаны в память.

Правило: увидел чекпоинт сжатия → **немедленно** `session_start(project=<slug>)`
ещё раз, до продолжения работы. Память в графе сжатию не подвластна; перечитка
восстанавливает решения владельца, открытые баги и задачи дословно.

## 2. Во время работы — «пиши сразу»

> **Ф5**: если на хосте установлены захват-хуки (`hooks/maxgraph_hook.py` → `/api/ingest`),
> поток действий (промпты, вызовы инструментов, стоп/конец сессии) пишется АВТОМАТИЧЕСКИ —
> это основной канал захвата. Ручная запись ниже остаётся обязательной для durable-фактов,
> которые хуки не видят (решения, итоги, связи), и fallback'ом там, где хуков нет.

Сохранять **немедленно**, не в конце сессии:

| Что произошло | Действие |
|---|---|
| Новый проект/сервис/файл/инструмент | `create_entities` (с `title`, `entityType`, `tags`) |
| Новый durable-факт о существующем | `add_observations` |
| Объект X использует/зависит от Y | `create_relations` (`depends on`, `configured by`, `hosted on`, `part of`…) |
| Изменился статус/параметр | `add_observations` (новый факт с датой) + при смене имени — `update_entity` |
| **Факт устарел** (старая цена, отменённое решение) | `add_observations(supersedes=["точный старый текст"])` — старая строка помечается `[~дата]` и уходит из поиска/session_start, оставаясь в архиве (read_graph/open_nodes видят всё). Ошибся — `update_entity(restore=[...])` снимает маркер. Физическое удаление — `delete_observations` работает всегда |
| Открытое дело «на потом» (work_state, В2.1) | `task_add(project, title, note?)` — задача висит в «Открытые задачи» session_start, пока её не закроют `task_done(project, name)`; текущий список — `task_list(project)` |
| **Баг исправлен** | `update_entity(status="fixed")` + `add_observations`: ГДЕ исправлено (коммит/файл:строки) и чем проверено. Без этого баг останется «открытым» для следующих сессий |
| **Задача/хвост сделан** | `task_done(project, name)` + факт с датой и ссылкой на реализацию |
| **Просьба (request) выполнена** | факт с датой на той же сущности: что сделано и где |
| Файл/модуль изменён | сущность типа `file`/`code` + связи к зависимостям |
| Сессия с важным результатом | сущность `entityType:"session"`, факты = итоги, связи `discussed` к затронутым сущностям |

### Heartbeat work-state — после каждого этапа

Завершил этап (закрытый пункт плана, отданный результат) → **одним датированным
фактом** обнови открытую задачу: `add_observations` на `task-<slug>` в формате
«сделано X → дальше Y». После этого сжатие контекста или обрыв сессии не страшны:
следующий `session_start` покажет, на чём остановились. Новых задач ради heartbeat
не создавай; нет открытой задачи по теме — факт пиши на сущность темы.

### Перед работой по теме — прочитать, что уже есть

Прежде чем что-то делать/чинить/искать: `search_nodes` по теме (или `session_start`
на старте). В графе уже лежат решения владельца, открытые баги, отложенные задачи и
итоги прошлых сессий — игнорировать их = переделывать сделанное и ломать решённое.
Нашёл закрытый баг/задачу — не переоткрывай без причины; нашёл открытый — работай с ним,
а не создавай дубликат.

### Правила качества

- **Имена**: `name` — kebab-case id навсегда; `title` — человеческое русское имя (оно показывается в дашборде)
- **Факты атомарны**: одно наблюдение = один факт, со ссылкой на дату/версию, если важно
- **Связи в активном залоге**: «uses», «depends on», «configured by» — не «is used by»
- **Не дублировать**: `create_entities` пропускает существующие; перед созданием — `search_nodes`

## 3. Зависимости кода и файлов

При изменении кода/конфигов агент обязан обновить граф:

- новый файл → сущность `file:<path>` + связь от владельца (`part of`)
- изменение конфигурации → факт на сущности сервиса + связи `configured by`
- удаление → удалить сущность/связь

## 4. Конец сессии

1. Один вызов `session_close(project, summary, done=[...], links=[...])` — создаёт или
   домердживает сущность сессии дня `session-YYYY-MM-DD-<slug>` с итогами и связями
   `discussed` (links пуст → связи собираются механически из сегодняшнего пульса).
2. Проверить `open_tasks_hint` в ответе — закрыть сделанное через `task_done`.
3. Обновить MEMORY.md (он читается первым)

Если агент забыл закрыть сессию, на следующем `session_start` появится секция
«## Незакрытая сессия» (≥5 пишущих событий за день и нет тега `session-close`)
— закрой задним числом тем же вызовом. Напоминание механическое: ничего не пишет.

## 5. Таймлайн

Каждая мутация автоматически пишется в `events.jsonl` — вкладка «Таймлайн» в дашборде показывает живую историю.

### Захват-хуки (Ф5): основной канал захвата

Если на хосте агента установлен `hooks/maxgraph_hook.py` (установка — `hooks/README.md`:
Claude Code `settings.json` или DSH `cordis.patch.yml`), события `SessionStart`/
`UserPromptSubmit`/`PostToolUse`/`Stop`/`SessionEnd` автоматически уходят на сервер:
локальный spool `~/.maxgraph/spool.jsonl` → `POST /api/ingest` батчами по 100
(fail-open: офлайн → доставка при появлении сети; идемпотентность по content-hash —
повторная доставка не дублирует). Каждое событие становится записью пульса
`hook_<name>` (`source="hook"`, дайджест ≤200 символов, с slug проекта), `SessionEnd`
дополнительно создаёт сущность `session-YYYY-MM-DD-<полный slug>` («завершена, N событий»)
один раз на проект в день (до 0.14.1 — 4-буквенный префикс slug, коллидировал) и,
если хост передал `data.open_tasks` (список строк, В2.1), — открытые task-сущности
проекта (дедуп по title среди ещё открытых: уже висящее дело не дублируется).
Хуки НЕ заменяют ручную запись §2: решения владельца,
итоги и связи хук не видит — их пишем сами. Нет хуков — протокол §2 остаётся
единственным (fallback) каналом.
